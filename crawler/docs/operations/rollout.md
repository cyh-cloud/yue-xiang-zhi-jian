# 上线顺序

状态: draft

日期: 2026-10-19

本文给出采集系统从官方来源到业务库的推荐上线顺序。每阶段必须通过 `validation.md` 的验收清单后才能进入下一阶段。

## 总原则

- 先官方来源，后行业站，最后聚合来源。
- 先只读采集和人工审核，后转换器和业务写入。
- 每次上线只扩大一个变量: 来源数量、字段范围或写入范围。
- 每个阶段保留回滚点、运行 ID、导入批次和样本证据。
- 不确定字段写 null 或“待验证”，不为了上线完整度编造数据。

## P0 官方来源

### 1. `ihchina` 非遗项目

- 先跑列表 JSON 全量发现，核对 3610 子项、361 页和 ID 去重。
- 再回填详情、传承人、相关项目和资讯/学术元数据。
- 先只写 crawler std，不写 `crafts`。
- 人工抽检项目编号、批次、类型、申报地区、保护单位和详情 URL。
- 验证无教学步骤项目不会生成空壳步骤。

### 2. `aqsc-moa` 名特优新和特质农品

- 先补齐来源文档中的公告列表、详情和附件 URL。
- 以已下载的两份 XLSX 作为字段回归样本。
- 核对省份、县域、产品名、获证/申请单位、联系人、生产规模和主要生产经营单位。
- 只能宣称已验证的 2025 年第三批，不先推断历史全量。

### 3. `cnipa` 地理标志

- 先验证公告列表和详情接口。
- 再下载 PDF，按页表头和“附件 2”分段解析产品行。
- 核对公告号、栏目日期、PDF 落款日期、省份、申请人、产地范围和详情 URL。
- 扫描件和无文字层 PDF 进入人工复核，不直接发布。

### P0 出口条件

- 三个来源的样本和详情 URL 可复现。
- 认证类型字段分开。
- 非遗 3610 与 1557 口径不混用。
- raw/stage/std 都可回溯到来源 URL 和哈希。

## P1 招聘、天气和方言

### 4. 招聘来源

- 先 `nzrc`、`nongmuhr`、`5ajob` 各自跑通列表发现和详情样本。
- 先只写 `recruitment_postings` 和 `recruitment_posting_sources` 的 std 契约。
- 跑农业相关性过滤并保留反例。
- 验证不访问简历、个人页和登录后联系方式。
- 明确不写 `job_listings` 和 `recruitments`。

### 5. 天气候选

- 先只做实时接口请求、缓存和字段解析。
- 核对城市编码、观测时间、取回时间和来源 URL。
- 不建历史天气表。
- 预警和预报字段未验证前只标记待接入。
- 农时提示先使用温度、降雨、风力和湿度，不做地块级结论。

### 6. 方言来源

- 先 `dialect-org` 的 15 条公开词条和详情。
- 建立 `dialect_points`、`dialect_lexemes`、`dialect_lexeme_sources` 的 std 契约。
- 现有 `dialects` 和 `dialect_phrases` 继续只读服务前台。
- 音频不可播放时写 `invalid`，不写可播放 URL。
- `cass-linguistics` 只接公开研究资料，不接登录后语料。
- `zhongguoyuyan.cn` 保持 `robots-restricted`，只登记。

### P1 出口条件

- 招聘岗位可跳转原详情，过期状态可识别。
- 天气只作为运行时参考，业务库无历史天气表。
- 方言规范化表与现有展示表并行，不破坏旧接口。

## P2 聚合来源

### 7. 聚合与补充来源

- 引入 `cnopendata`、`feiyiw` 和其他二次整理来源。
- 聚合来源只补缺，不覆盖官方原始公告。
- 每条聚合记录保留官方来源或详情 URL。
- 无法回溯官方的记录进入人工复核。
- UGC 和无法核验来源不进入业务发布。

### P2 出口条件

- 来源优先规则可执行。
- 冲突记录保留双方来源 URL。
- 聚合来源不会改变官方认证类型和自然键。

## 数据库与转换器

### 8. 采集库 schema

- 先建 raw、stage、std 三层和来源引用。
- 再建冲突、导入批次、人工字段保护和回滚记录。
- 只落地已经通过验收的字段，不预先建历史天气表。
- 采集库 schema 与 `schema/crawler-db.md` 对齐。

### 9. 业务库变更

- 认证农产品表和来源表建议新增。
- 招聘岗位表和来源表建议新增，现有 `job_listings`、`recruitments` 保持不变。
- 非遗扩展字段优先放 `crafts.extra` 或建议关联表。
- 方言规范化表建议新增，现有三张展示表保留。
- 天气不建表。
- 业务库变更单独评审，不在本文直接执行。

### 10. 转换器

- 转换器只读取 std 层。
- 先 dry-run 输出差异报告，不直接写业务库。
- 再按导入批次写少量样本。
- 验证自然键、幂等 upsert、官方优先、冲突记录和人工字段保护。
- 最后开放批量导入和按批次撤销。

### 数据库出口条件

- 每次导入有批次和回滚记录。
- 重复导入不产生重复业务记录。
- 人工修改字段不被覆盖。
- 现有前端 API 契约不因新表或 `extra` 字段改变。

## 人工复核

### 11. 人工复核批次

- 第一批只复核 P0 官方来源的样本和冲突。
- 第二批复核招聘农业相关性和过期状态。
- 第三批复核方言词条、音频和展示映射。
- 第四批复核聚合来源和冲突裁决。
- 复核记录写入 `crawler/docs/reviews/`，不写业务库审核状态代替审核记录。

### 复核通过标准

- 来源、详情 URL、自然键和目标表一致。
- 未知字段保持 null。
- 个人信息和受限正文未进入错误位置。
- 没有空步骤、空视频或伪造的天气预警。
- 运营手工修改字段有保护标记。

## 回滚顺序

按上线顺序的反向回滚:

1. 停止新的转换器批次和调度。
2. 撤销最近导入批次中未被人工修改的记录。
3. 删除或停用该批次新增的来源关联。
4. 恢复上一版业务库快照或按回滚记录恢复字段。
5. 保留采集库 raw、stage、std 和导入日志用于调查。
6. 回退业务表变更，先停写再迁移，禁止直接删除有引用的表。
7. 回退页面发布开关，保留来源链接和只读基础资料。
8. 最后回退采集库 schema 和转换器版本。

回滚不得:

- 删除人工修改过的运营内容。
- 删除来源证据和哈希。
- 用 `DROP TABLE` 直接处理含业务数据的表。
- 把回滚失败伪装成成功。

## 待验证

- 各阶段的具体时间窗口和负责人。
- 业务库迁移的正式评审流程。
- 回滚记录是否需要独立审批。
- 生产调度、监控和告警的接入方式。

# ADR 0001：采集库与业务库分离

状态：已接受

日期：2026-10-19

## 背景

粤乡智匠当前使用一份 SQLite 业务库，承载学员、内容、招聘、农时、方言和手工技艺等在线业务。采集系统需要保存原始 HTML、JSON、XLSX 和 PDF，保留同一来源的多次响应，处理来源字段变化、跨来源冲突、人工复核和分批撤销。把这些状态直接写进业务库，会让业务表同时承担展示、抓取审计和数据血缘，增加迁移风险，也会让业务 API 读到未审核或已过期的数据。

采集系统还面对多个来源、不同访问等级和不同更新频率。原始页面与被标准化的实体不是同一种生命周期，必须分开保存。

## 决策

采用两套 SQLite 数据库和一层转换器：

1. 采集库独立存在，分 `raw`、`stage`、`std` 三层。`raw` 保存响应和文件元数据，`stage` 按来源原始形状保存，`std` 保存跨来源标准实体。
2. 粤乡智匠业务库只保存展示、审核和运营所需的数据，不保存抓取状态、重试记录、原始 HTML、来源差异和完整附件。
3. 转换器只读采集库 `std` 层，不直接读页面、不直接读 `raw` 或 `stage`，也不发起网络请求。
4. 转换器按自然键升级写入业务库，记录导入批次，冲突写入采集库的 `import_conflicts`，支持按批次撤销尚未被人工修改的结果。
5. 采集库与业务库使用不同的数据库连接和部署路径。转换器是唯一跨库写入者，业务代码不直接读取采集库。

## 数据流

```text
来源页面 / API / 附件
        |
        v
crawler.db: raw -> stage -> std
                          |
                          v
                      转换器
                          |
                          v
yuexiang.db: 已发布、可审核、可运营的数据
```

## 备选方案

### 方案 A：所有数据直接写入业务库

不采用。业务表会被原始 HTML、文件哈希、抓取失败和来源差异污染；未发布数据可能与在线内容混在一起；来源变化时会直接改动业务 schema。出错后也难以判断一条记录来自哪个响应、哪个批次。

### 方案 B：只保留一份采集库，业务前台直接查询

不采用。审批、发布状态、人工字段保护和现有 API 契约都在业务库侧；让前台依赖采集库会把爬虫结构变化传导到页面，且无法隔离未审核数据。

### 方案 C：使用外部数据仓库或对象存储

当前阶段不采用。项目是单机 SQLite 部署，新增服务会增加运维和权限复杂度。设计保留文件路径和哈希字段，未来可以把原始文件迁到对象存储，转换器契约不变。

### 方案 D：每个来源一个数据库

不采用。跨来源的标准实体、冲突和批次无法在单事务中处理，来源数量增加后连接和备份成本更高。来源隔离改由 `source_id`、`stage_*` 表和来源文档承担。

## 后果

### 正面

- 原始响应与业务展示解耦，能够按记录回溯到 URL、取得时间、哈希和导入批次。
- 采集重跑、来源更换、规则调整和批次撤销不会直接破坏在线表。
- 业务库可以保持现有 API 和已有表结构，新增内容通过独立表或明确补列演进。
- `raw`、`stage`、`std` 的职责清晰，转换器有稳定的单一输入契约。
- 允许全量非遗“可浏览”与“可教学”使用不同发布策略，避免空教学页。

### 负面

- 需要维护两个数据库文件、两套备份和跨库一致性检查。
- 转换器必须处理幂等、自然键、冲突和人工字段保护，不能采用简单覆盖。
- 原始响应和文件会增长，必须执行保留策略和容量监控。
- 运维需要明确采集库可丢失原始快照但业务库不可丢的恢复优先级。

### 约束

- 转换器写入业务库时不复制账号密码、Cookie、登录后页面或个人简历。
- 每次跨库导入必须能定位到 `import_batches` 和 `import_conflicts`。
- 本次只冻结设计，不创建数据库、不写迁移、不修改后端代码。

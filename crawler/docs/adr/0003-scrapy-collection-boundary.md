# ADR 0003：Scrapy 采集执行边界

状态：已接受

日期：2026-10-21

## 背景

当前采集层由手写发现器、请求代码、来源解析器和统一运行入口组成。实时请求、文件读取、原始证据落库、发布门禁和候选标准实体写入集中在同一条运行路径里，来源差异主要靠条件分支和来源模块处理。随着来源增加，这种做法会让站点选择器、限流、浏览器依赖和失败处理继续耦合，也容易在多个来源之间复制同一套证据、去重和发布逻辑。

现有来源的形状差异很大：`ihchina` 使用分页 JSON 和详情页，`aqsc-moa` 与 `cnipa` 以 XLSX、PDF 或公告附件为主，招聘和方言来源依赖不同分页、表单或详情结构，部分来源还需要浏览器执行脚本。它们共享来源登记、访问等级、版权、证据、发布门禁和候选标准实体契约，但不共享站点选择器和运行参数。

迁移需要同时满足两个目标：每个站点可以独立演进，所有站点又使用同一套采集库契约。Scrapy 提供成熟的项目隔离、调度、下载器中间件、爬虫中间件、Item Pipeline、重试、限速和扩展机制，适合作为默认采集执行层。现有手写实现和 fixture 测试已经承载了来源边界与发布规则，迁移不能借机放松这些约束。

## 决策

### 1. Scrapy 是默认采集执行层

所有新的业务内容实时采集实现默认使用 Scrapy。现有手写实时实现按来源逐步迁移，迁移完成的来源以 Scrapy 项目作为唯一实时执行入口。目标形态是完整迁移到 Scrapy，不以长期维护两套实时采集实现为目标。天气运行时客户端不适用本条，见第 7 条。

### 2. 一个采集网站一个 Scrapy 项目

一个业务内容采集网站对应一个独立的 Scrapy 项目，项目身份沿用来源注册表中的 `source_id`。项目拥有自己的 Spider、settings、middlewares、pipelines、站点解析规则和站点运行说明。来源文档允许的子资源继续属于同一来源和同一项目，不因为域名或访问边界不同拆成第二个来源。

站点之间不共享 Spider，也不通过一个参数化 Spider 承载多个网站。共享能力进入共享包，站点差异留在项目内。

### 3. 共享包承载公共采集契约

共享包提供所有 Scrapy 项目共用的采集中间层，至少包括：

1. 原始证据契约和持久化，包括请求、最终 URL、响应、哈希、取得时间、locator 和文件元数据。
2. 采集库写入，包括 raw、stage 和候选标准实体。
3. 来源注册表读取、来源状态判断、访问等级和版权字段。
4. 统一发布门禁。
5. 去重键、规范化键和重复运行处理。
6. 结构化运行日志、计数、错误和运行标识。
7. robots 事实读取、保存和访问结论记录。

共享包不包含站点选择器、站点限速值、站点分页规则、站点授权判断或业务字段映射。项目只组合共享契约，不复制共享实现。

### 4. Item 与 Pipeline 的边界止于采集库

Scrapy Item 表达已解析、待验证的采集结果。项目 Pipeline 可以把 Item 写入采集库的 raw、stage 和候选标准实体，也可以执行来源内校验、去重、发布门禁和失败记录。管线边界止于采集库。

Scrapy 项目、Item 和 Pipeline 不打开业务库，不导入业务库写入模块，不调用转换器，也不承担业务表映射。

### 5. 转换器保持独立

转换器是 Scrapy 运行之外的跨库阶段。它从采集库读取候选标准实体，执行自然键、来源优先、冲突、人工字段保护、发布资格判断、转换批次和回滚，并把结果写入业务库的业务实体。业务实体只有通过审核并对外展示后才成为发布实体。Scrapy Pipeline 不替代转换器，也不把业务写入包装成采集管线。

当前转换器是否处于 dry-run、写入开关和审核流程不因本 ADR 改变。

### 6. 采集库 `std` 与业务库术语分离

本 ADR 统一以下术语：

| 术语 | 含义 |
| --- | --- |
| 采集库 std / 候选标准实体 | 采集库中跨来源统一后的候选实体，有来源关系和候选发布状态，但不等同于业务实体，也不等同于发布实体。 |
| 业务实体 | 业务库中承载业务生命周期的一条记录，包括草稿、审核中、阻断和已发布等状态。所有业务库记录都是业务实体。 |
| 发布实体 | 业务库中已经通过审核并对外发布的业务实体，是业务实体的子集。 |

物理表和代码标识继续保留已冻结的 `std_*` 名称，以兼容现有 schema 和契约。文档中的 `std` 单独出现时，只能指采集库候选标准实体，不能指业务实体或发布实体。

### 7. 天气运行时客户端不进入 Scrapy 迁移

天气查询是运行时 API 客户端，不是 Scrapy 采集项目，也不进入采集库、转换器、发布门禁或 Scrapy 调度。`weather` 继续负责发起请求、解析天气 DTO 和使用 15 分钟运行时缓存。`open-meteo` 和 `qweather` 保持 `draft` 与禁用状态，只保留候选来源元数据，不建立可执行 Spider。

天气结果不因本 ADR 变成持久化采集任务。若未来要把天气响应写入采集库，必须先单独确认来源范围和数据用途。

### 8. 单一 uv 依赖根与 fixture 位置

迁移使用 uv。依赖版本只在 `crawler/pyproject.toml` 与 `crawler/uv.lock` 中维护，各项目不复制锁文件。项目目录仍是独立的代码、配置和测试单元，站点依赖在共享项目元数据中按项目声明。

测试 fixture 统一位于 `crawler/tests/fixtures/<source_id>/`，每个项目只引用自己的子目录，不在项目目录内复制 fixture。

## 数据流

```text
采集网站
   |
   v
Spider
   |
   v
Item -> 共享 Pipeline -> crawler.db: raw 证据 -> stage -> 候选标准实体
                                                        |
                                                        v
                                  转换批次 -> 冲突 / 人工复核
                                                        |
                                                        v
                                           yuexiang.db: 业务实体
                                                        |
                                                        v
                                  审核通过并对外发布 -> 发布实体
```

## 后果

### 正面

- 站点依赖、运行参数和 Spider 实现相互隔离，一个站点改版不会迫使其他站点一起发布。
- 原始证据、来源判断、发布门禁和去重只有一套共享实现，减少项目之间的行为漂移。
- 迁移可以按来源验收和切换，不需要一次性重写当前采集层。
- Scrapy 项目与转换器职责清晰，采集失败不会直接改变业务库。

### 负面

- 每个项目都要维护自己的 settings、运行说明和测试入口，项目数量增加后运维成本上升。
- 共享包升级需要同时验证多个项目，必须保持向后兼容。
- 来源迁移期间会同时存在旧实现、fixture 测试和新项目，切换纪律比单实现更严格。
- 每站独立项目会增加仓库目录和测试入口，依赖升级需要在共享 `uv.lock` 中统一回归。

### 约束

- 一个来源在同一时刻只能有一个实时写入者，避免旧实现和 Scrapy 项目双写采集库。
- 任何 Scrapy 项目都不得直接写业务库。
- 共享包变更必须通过公共契约测试，并在至少一个已迁移项目中通过 fixture 回放。
- 站点依赖在共享 `pyproject.toml` 中按项目声明，并只由该项目的运行和测试入口选用；共享包不依赖任何站点专用包。
- 发布门禁、访问等级和版权边界继续以 [ADR 0002](0002-source-rights-and-access.md) 与来源注册表为准。

### 迁移顺序

1. 先冻结共享 Item、证据、采集库写入、来源判断、发布门禁、去重、日志和 robots 契约。
2. 用 8 个项目之一的 fixture 路径验证共享包，不新增第九个 demo 项目。
3. 为 8 个项目建立独立骨架、fixture 回放和接口契约测试。
4. `ihchina`、`nzrc`、`nongmuhr`、`dialect-org`、`cass-linguistics`、`feiyiw` 在站点允许时完成 5 个列表页和 5 条详情记录的实时样本验证。
5. `aqsc-moa` 和 `cnipa` 只完成项目骨架、fixture 和接口契约测试，不执行实时文件采集。
6. 只有完成实时验证和来源审核的项目才进入写入权切换；受阻项目保留 fixture 结论并记录阻塞证据。
7. 每个已切换来源通过观察期后单独退役旧实现。

## 迁移与验收护栏

1. **先契约，后站点。** 共享包先覆盖 raw 证据、采集库写入、来源判断、发布门禁、去重、日志和 robots 事实，再迁移第一个实时来源。
2. **fixture 保留。** 现有 fixture 测试继续作为来源回归基线。Scrapy 项目必须能离线回放同一 fixture，并保持文档要求的字段、URL、locator、版权和跳过结果。
3. **实时样本范围固定。** 前六个项目在站点允许时验证 5 个列表页和 5 条详情记录；`aqsc-moa` 与 `cnipa` 不执行实时文件采集。
4. **单来源切换。** 旧实现保持实时写入权，直到对应 Scrapy 项目完成离线回放和隔离实时 canary。切换以来源为单位一次性完成。
5. **隔离验收。** canary 使用独立的采集库、下载目录和运行标识，不写正式采集库，不写业务库。
6. **发布门禁不放松。** `aqsc-moa` 和 `cnipa` 在迁移前后保持相同发布边界。没有可直接打开的长期详情 URL 的记录仍只进入 raw/stage，不进入候选标准实体或发布实体。
7. **失败必须显式。** 404、403、429、5xx、robots 结论、登录边界和解析失败都要记录；空结果不得伪装成成功。站点封锁导致实时验证失败时，记录封锁 URL、时间、状态码或错误、证据位置和重试条件。
8. **实时结论不得替代。** 站点封锁时 fixture 和接口契约测试可以继续通过，但不得把 fixture 通过写成实时成功。
9. **重复运行幂等。** 同一 fixture 或同一实时样本重复运行不得产生重复候选标准实体或错误覆盖既有来源证据。
10. **无业务库写入。** 项目依赖、导入图和运行测试都要证明 Scrapy 运行不会打开业务库或调用转换器。
11. **可回退。** 切换后保留回退到旧实现的运行开关；回退不删除已保存的 raw、stage 或候选标准实体证据。
12. **来源审核完成。** 每个来源的切换结论写入对应审核记录，说明样本、计数、证据、缺口和回退方式。

## Scrapy 能力边界的认定

只有在出现可复现的 Scrapy 能力边界时，才考虑为单个来源引入其他框架。能力边界必须同时满足：

1. 目标公开工作流无法通过 Scrapy 文档化的 Spider、Downloader Middleware、Spider Middleware、Scheduler、Addon、Item Pipeline 或受支持扩展实现，或者现有扩展会导致无法接受的正确性、访问控制或资源问题。
2. 边界有最小原型、失败测试或运行证据，能说明具体站点、请求、缺失能力和失败结果。
3. 替代方案不绕过登录、验证码、付费墙、robots 结论或其他访问控制，也不改变发布门禁。
4. 替代框架只作用于该来源项目，继续使用共享 Item 契约、原始证据和采集库写入，不扩散成全站默认。
5. 项目负责人以新的架构决策或明确的范围记录批准例外。

以下情况不构成能力边界：不熟悉 Scrapy、希望复用现有脚本、Scrapy 没有现成选择器、需要浏览器执行脚本、需要解析 XLSX 或 PDF、需要自定义重试或限速。浏览器自动化、文件下载和文件解析优先通过 Scrapy 的受支持扩展或项目内 helper 完成。

## 本次范围、项目清单与排除来源

- 本次只写文档，不安装 Scrapy，不实现 Spider、Pipeline 或共享包，不修改采集库 schema。
- 本轮范围恰好是 8 个 Scrapy 项目：`ihchina`、`nzrc`、`nongmuhr`、`dialect-org`、`cass-linguistics`、`feiyiw`、`aqsc-moa`、`cnipa`。
- `ihchina`、`nzrc`、`nongmuhr`、`dialect-org`、`cass-linguistics`、`feiyiw` 在站点允许时完成 5 个列表页和 5 条详情记录的实时样本验证。
- `aqsc-moa` 和 `cnipa` 只完成项目骨架、fixture 和接口契约测试，不执行实时文件采集。
- `5ajob` 的权利状态保持 `prohibited`，`zhongguoyuyan` 保持 `excluded`，`cnopendata` 保持 `deferred`，三者都不是可执行项目。
- `open-meteo` 和 `qweather` 保持 `draft` 与禁用状态，不是可执行项目，也不建立 Spider。
- `weather` 是运行时 API 客户端，负责 DTO 解析和 15 分钟缓存，不属于 8 个 Scrapy 项目。
- 不新增来源，不修改来源状态，不放松任何现有发布门禁。

## 备选方案

### 方案 A：所有网站共用一个 Scrapy 项目

不采用。站点设置、依赖、选择器和失败模式会互相污染，一个站点升级可能迫使全部站点回归。来源隔离应由项目边界承担，通用能力由共享包承担。

### 方案 B：一次性重写整个采集层

不采用。当前 fixture、发布门禁和来源文档已经承载了可验证行为，一次性重写会让所有来源同时失去回退点，也难以定位行为回归。

### 方案 C：由 Scrapy Pipeline 直接写业务库

不采用。它违反 [ADR 0001](0001-crawler-separate-database.md) 的跨库边界，绕过转换批次、冲突、人工字段保护和回滚。

### 方案 D：用 Scrapy Pipeline 替代转换器

不采用。转换器处理跨来源自然键、业务实体写入和发布资格，不属于单个采集项目的运行边界。替代它会把这些规则拆散到各站点项目中。

### 方案 E：预先引入另一个采集框架

不采用。没有经过证实的 Scrapy 能力边界时，第二套框架只会增加契约、依赖和运维分叉。出现边界后，也只允许单来源、可回退的例外。

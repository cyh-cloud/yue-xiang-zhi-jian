# Spec：内容数据全部落库，代码零硬数据，删掉数据层转发层

## Problem Statement

平台的数据散落在九个地方：一份 SQLite 库（36 张表），加上代码里六份内容数据模块
（农时日历、病虫害知识、实拍图清单、招募公告、成功案例、政策），以及三份混在路由
文件里的内容常量（手工技艺、方言知识、作物兜底目录）。同一个事实经常有两份副本，
例如作物中文名同时存在于 `farming_data.py`、`pest_data.py`、`AGRICULTURE_KNOWLEDGE`、
`_AGRI_PRODUCT_NAME_FALLBACK` 与前端 `PRODUCT_NAMES`。

更严重的是启动时的「签名重灌」机制：代码里的内容算了 sha1 指纹，与库里存的不一致
就 DELETE 全表再按代码重插。这导致三个后果：

- 农技人员在后台标记的复核结论、运营改过的内容，只要有人改了对应的 `*_data.py`，
  下次启动就被冲掉。人工结论不可持久。
- 每次启动都要把全部内容 JSON 序列化一遍算指纹，再加全表 DELETE + INSERT。
  内容涨十倍，启动从 5 秒变 50 秒。
- `farming_tasks.id` 每次重灌都变（库里实测起点 431，正是历史重灌的痕迹），
  而这个 id 直接下发给前端。

另外两件事同批解决：

- 内容只能改代码再重启才能更新，没有一个界面能让运营或农技人员直接维护。
  而平台已设计了五个角色，其中没有一个是管内容的。
- 数据层有一个 163 个符号的纯转发层（`database.py`），它零逻辑，却被一条机械检查
  锁死「外部必须走它」。它让「某个调用打到哪份数据」变得看不出来。
- 领域之间禁止 import 的硬约束，逼得 5 个路由文件绕过数据层直连 SQL 写别人的表。

## Solution

把代码里所有内容数据搬进 SQLite，删除内容数据模块与签名重灌机制，让 SQLite 成为
唯一数据源。同时新增「运营」角色与运营后台，让内容可在线维护。数据层职责按域重划，
删掉转发层，跨域多表查询改用视图。

数据库引擎不变，继续用 SQLite。275 处业务 SQL 与 20 个测试文件的绝大部分不动。

## Implementation Decisions

### 权限模型（第一步，零数据变化）

- 新增 `backend/core/permissions.py`，持有全站唯一的能力表。角色与能力的对应集中在一处，
  不再散落 `role != 'x'` 硬判。能力命名 `<域>.read` / `<域>.manage`，空元组表示公开。
- 能力表覆盖：农时、病虫害、技艺、方言、招募、案例、政策、课程、岗位、用户、审核。
  「运营不能管用户、不能审核」是表里显式的两条，不是「十处都没写它」。
- 每个 `db_domains` 模块标注它服务的能力域，让机械检查有判据。
- 新增 `require_capability` 装饰器，与既有 `require_role` 并存，路由逐个切换。
- ADR 0001 的「领域之间不得互相 import」修为「不得访问不具有该角色权限的数据」。
  运营角色出现后跨域是常态，禁止 import 已不适用。
- `tools/check_architecture.py` 的跨域 import 检查改为按能力表判权。它抓住结构性越界
  （某域代码 import 了它无权访问的数据模块），抓不住函数内的动态绕过，后者靠 API 测试覆盖。

### 新表（20 张）

沿用现有命名风格：snake_case 复数、`is_` 前缀布尔、`_at` 后缀时间、TEXT 存 JSON 数组。

- 农时：分类标签表（替代 `FARMING_CATEGORY_LABELS`）
- 病虫害：作物表、条目表、来源表、条目与来源多对多表、实拍图表
- 招募：公告表、公告来源表
- 案例：案例主表 + 四个子表（数据指标、里程碑、来源、借鉴点）
- 方言：方言表、短语表、快捷问题表
- 技艺：技艺表、步骤表、采购分类表、采购条目表、预算表

条目表的症状、防治、预防、登记药剂、用量表五列存 JSON 文本，读取侧由兼容层解析。
`farming_tasks` 与 `pest_entries` 各补 `verified_by` 与 `verified_at` 两列，
作为既有 `is_verified` 的必然延伸（现在只记结果，不记谁核的、何时核的）。

### 每张表一个预留列

全部表（含既有 36 张）加 `extra TEXT NOT NULL DEFAULT '{}'`，存 JSON。
不建索引：当前没有任何查询走这一列。等真有需求时在同一处迁移里补，并写清为什么。

### 删除的数据（不再是数据，是缺陷）

- 作物目录兜底表（6 作物）：表读空时应明确失败，不该退回半份数据
- 静态建议问题（6 作物）：AI 不可用时建议栏应明说不可用，不给一份看似可用的假建议
- 作物中文名兜底表与农业知识常量：改读作物目录表，消除五处作物名副本

物候期命中判定与提醒摘要两个纯函数保留，移入数据层农时模块。

### 留在代码里的

用药数值正则与免责声明原文、节气算法、评分规则、状态标签、作物白名单、AI 提示词模板、
AI 降级文案生成器。判据是「改它需要谁」：规则由开发改，留代码；内容由运营改，进库。
AI 相关文本本次不动，留待 AI 模块大改时一并处理。

### 视图（5 个）

- 企业看申请人（四表 JOIN：投递、岗位、用户、简历）
- 企业岗位统计（两表 JOIN + 分组计数）
- 首页统计（跨三个域的三次计数）
- 批改时取提交上下文（提交 JOIN 作业）
- 审核详情取 3D 模型

视图定义与建表语句同住 schema 模块。域路由只查视图，域间 import 边为零。
剩下 13 处直连 SQL 是「写别人的表」，收进对应域的数据模块；
审核记录的跨域删除收敛为一个入口，与既有审核分派表同形状。

### 删除转发层

删掉 163 个符号的纯转发模块。数据层接口就是各域数据模块本身，调用方按域 import。
它的五个调用方全是启动入口或测试，没有一个业务调用方；而数据层 18 个模块之间
本来就直接互相 import，从不经过它。删除测试下复杂度消失而非扩散。

### 删除签名重灌

删除三个签名函数、两张签名元数据表、以及全部播种逻辑。启动路径只做建表与补列。
演示账号与演示岗位、门户轮播与公告、讨论区热帖，改为一次性迁移灌入。
新环境部署改为「还原一份基线库文件」，仓库里不保留内容副本。

### 速查接口改服务端筛选

这是本次唯一一处对外接口变化，需单独记录。

- 后端早已支持作物、类型、关键词三个筛选参数，前端一个都没用，改为前端传参
- 新增分页参数，默认每页 50 条；响应新增筛选后总条数
- 作物按钮的计数语义改为「当前筛选条件下该作物的条数」，与按钮天然一致
- 前端删掉本地筛选，改为请求驱动，关键词输入加防抖
- 不动的：卡片字段、详情弹窗、免责声明、统计、空态与错误态措辞
- 「来源没给就显示未提供」「无授权图不冒充」两条硬约定原样保留

### 迁移脚本

一次性脚本把代码内容灌进新表，跑完验证通过后归档。脚本进版本库但标注「已执行」，
靠迁移记录表防重入，不删。理由：它是 6400 行内容进库的唯一凭据，发现漏字段时
重跑比手工补快；且它是转换逻辑，不是数据副本。

迁移前必须处理的现库脏数据（均已实测）：积分表 2 行主键为空、
消息表 2 行收件人指向不存在的用户。清理动作记录到迁移日志，不静默丢弃。

### 数据层其它修正

- 新增学员时的学号生成有并发竞态（先查最大号再 +1），改为查重重试
- 24 处「多语句单连接」中只有 6 处需要真事务，把名单写进注释，避免有人在中间插语句

### 部署

- 去掉 serverless 部署配置与入口文件。serverless 无持久盘，且内存与超时限制不适合本项目
- 改为自托管单机部署：Flask 裸跑 + 多线程，静态文件继续由 Flask 伺服
- 数据库文件加进忽略清单，不再进版本库

## Testing Decisions

好的测试只测外部行为，不测实现细节。本次的测试面是 **API 层**，用 Flask test client
打接口，断言状态码、响应结构、权限结果。仓库已有充足 prior art：14 个领域测试文件
共 384 个用例全部走这条路，13 个 e2e spec 覆盖 30 个接口。

必须新增或改写的测试：

- **权限矩阵**：每个能力 × 每个角色，一张表驱动。运营打用户接口必须 403，
  运营打内容管理接口必须 200，学员打管理接口必须 401 或 403。
- **契约快照**：重构前先抓一批接口的响应 JSON 存成基线，重构后逐字节比对。
  覆盖农业四个功能区、病虫害两条接口、技艺两条、方言两条。
  速查接口例外，单独比对「不带参数时返回的条目集合与字段」一致。
- **内容维护闭环**：运营经接口改一条农事任务，前台接口立即返回新值，无需重启。
- **复核追溯**：标记复核后 `verified_by` 与 `verified_at` 有值，且接口输出形状不变。
- **启动纯净**：启动两次，第二次不改变任何一行内容（替代原先的「种子幂等」断言）。
- **无硬数据**：机械检查，代码里不得出现内容字面量（扫描数据模块目录与已知常量名）。
- **机械检查自身**：临时给某个运营域路由加一句越界 import，检查必须报违规。
- **速查分页**：带 `limit` 时只返回指定条数，`total` 正确，翻页不重不漏。
- **视图等价性**：企业申请人接口在视图改造前后返回同样结构（这是既有测试，需保持绿）。
- **脏数据清理**：迁移脚本把两处脏数据清掉，且清理动作有日志。

删除的测试：锁死五个内容数据模块必须存在且内容不变的那个文件（352 行），
它与本次目标直接冲突，改写为「内容表有行 + 接口输出形状不变」。

保留的测试：纯 HTTP 契约测试全部保留，它是「对外输出不变」的守门人。

两个既有失败（教师学员列表与教师仪表板，原因是没带会话头）顺手修掉，
验收口径为「全绿」。

## Out of Scope

- AI 模块的任何改动：提示词模板、降级文案生成器、上游调用、模型选择。
  方言降级话术库里的用药数值与病虫害用量表不同源的问题，留待 AI 模块大改时处理。
- 数据库引擎更换。已评估并否决：本项目数据量与访问量下 SQLite 不是瓶颈，
  且换引擎的改动量与收益不成比例。
- 会话存储介质变更。登录凭证继续存 SQLite，不引入 Redis 或 JWT。
  过期会话即删，不留历史（现行行为本就如此，只是从未清理）。
- AI 对话历史的持久化。当前对话历史只活在前端内存，新增该能力是独立需求。
- 前端视觉与交互重做。本次只改速查的取数方式与新增运营后台页面。
- 多 worker 部署、反向代理、容器化。
- 既有接口的参数、字段、状态码、错误码（速查接口的分页参数除外）。

## Further Notes

- 执行顺序有强依赖：权限模型必须最先落地，否则机械检查无从判起；
  内容灌库后代码仍在读旧模块，两者暂时并存，删模块是切换点。
- 内容灌库后，运营改内容立即生效，不再需要重启。这是本次最直接的收益。
- 「运营」是「超级管理员」的子集：拿内容管理权，不拿用户管理与审核权。
- 现库的 `data/yuexiang.db` 被 git 跟踪且工作区版本比提交版本大 1MB，
  迁库前必须加进忽略清单，否则二进制数据继续沉淀在 git 历史里。

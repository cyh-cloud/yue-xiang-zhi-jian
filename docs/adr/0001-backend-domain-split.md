# 0001 后端按领域拆分，路由之间禁止互相 import

状态：accepted

`app.py` 曾是一个 6032 行的单文件应用，`database.py` 3346 行且 33 张表混在一个模块里，
领域边界只靠注释横幅分隔。决定把后端按领域拆成独立模块，并确立一条硬约束：
**领域路由模块之间不得互相 import**，跨领域需求一律经由共享层或显式的窄接口满足。

选择「领域优先于 URL 前缀」而非按前缀机械切分：`/api/teacher/*` 下混着名册、公告、
批改、学情、课程材料上传五种关注点，按前缀切会把它们捆成一个 680 行的模块。
但一个 URL 前缀可以拆成多个领域模块（如直播实训从 `/api/ecommerce/*` 中独立）。

选择「只搬移与提取，零对外行为变化」而非分层重构：23 个单测与 13 个 e2e spec 已把
URL、JSON 键与状态码锁死，重构内部签名的行为风险与本次收益不成比例。

## Consequences

- 每个领域一个 Blueprint，共享层只有 `core`、`ai`、`shared` 三个模块。
- 审核状态变更收敛为单一入口，由它按内容类型分派到各领域，领域侧只暴露「改我这张表的
  审核字段」一个窄接口。
- 跨领域聚合（如未读总数、能力档案）由持有方显式调用其他领域的窄接口拼装，
  不再直接读别人的表。
- 所有文件系统路径改为以仓库根为基准，不再以模块文件所在目录为基准。

## 修订：三个边界件上提共享层（T13 / T15 实施时补充）

spec 原本把三样东西裁定给某个领域、另一个领域「显式引用」：电商作物名校验归电商运营域、
直播实训域引用；实训状态标签归直播实训域、实训批改域引用；「是否已有简历」归就业能力
档案域、就业对接域引用。实施时发现这与「领域之间不得互相 import」直接冲突：显式引用
就是一条 import 边，机械检查必然报违规。

裁决改为**零领域状态者上提共享层**：三者都是无副作用的纯函数或纯查表，放共享层不违背
「共享层不感知任何具体领域」（同层的 `shared/options.py`、`shared/copywriting.py` 也是
这类）。落点为 `shared/ec_products.py`（作物白名单与 EC_* 额度）、
`shared/training_status.py`、`shared/resume_state.py`。

这样既满足机械约束，又保持全站一份真相，每处都用 `assertIs` 断言锁死域内引用与共享层
是同一个函数对象。**spec 的「归某域、另一域显式引用」表述自此作废，以本修订为准。**

同批还新增了一个 spec 未列出的配置面：`YUEXIANG_DB` 环境变量，让测试指向一份可弃的
数据库副本，避免 e2e 写坏真实数据。不设该变量时行为完全不变（仍用仓库根的
`data/yuexiang.db`）。

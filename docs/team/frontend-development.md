# 前端开发规范

本文件面向主要承担前端工作的团队成员。默认权限是前端交付，后端与数据库按 `backend-database-policy.md` 处理。

## 工作范围

- 页面结构、视觉样式、交互逻辑、响应式布局和可访问性。
- 前端模块、静态资源、前端数据展示和用户反馈。
- 与本次改动相关的前端测试与 e2e 场景。
- 现有 API 契约内的联调与错误态处理。

## 开始前

1. 确认需求目标和验收方式，避免只按截图猜行为。
2. 先读相关 ADR、`GLOSSARY.md` 和已有页面实现。
3. 纯前端 fix 或前端小功能可以留在当前分支；涉及后端接口、数据库结构或 API 契约时，从最新 `main` 新建功能分支。
4. 检查改动是否会触及 `backend/`、`data/`、`migrations/` 或 API 契约。会触及时，先创建带 `feat` 标签的 GitHub issue；有冲突时再添加 `conflict` 和严重程度标签，然后开工。

## 交付要求

- 改变现有 API 契约时，先提出接口需求，由项目负责人确认后实施。
- 前端临时展示可以使用本地状态，但不能用生产假数据掩盖缺失接口。
- 同时检查桌面端与移动端，关键交互要有明确的加载、空状态和失败反馈。
- 提交前运行与改动相关的单测、架构检查和 e2e；只跑通过的部分不能代替整体验证。
- 变更说明写清用户可见变化、验证证据、依赖的后端能力和未覆盖风险。

## 遇到后端问题时

记录页面、角色、操作路径、请求与响应、复现步骤和期望行为，提交给项目负责人判断。需要修改后端或数据库时，按 `backend-database-policy.md` 走 GitHub issue 与功能分支流程。

## Fix 与前端小功能

纯前端 fix 可以在当前分支直接 commit 和 push，不需要项目负责人审查。前端小功能仍按新功能流程创建带 `feat` 标签的 GitHub issue，但不触及后端接口、数据库结构、API 契约、ADR 或文档冲突时，也可以留在当前分支直接 commit 和 push，不需要另开功能分支或等待审查。提交前完成相关验证；触及受保护范围时，转为功能分支流程。

## 代码审查关注点

- 是否符合既有页面结构和视觉语言。
- 是否遵守 ADR 与 API 契约。
- 是否覆盖移动端、失败态和权限差异。
- 是否把后端或数据库改动混入未经授权的分支。

# 后端与数据库变更政策

默认开发范围是前端。后端与数据库由项目负责人维护。其他成员需要改动时，先在 GitHub issue 中完成讨论，再进入独立功能分支。

## 受保护范围

- `backend/` 下的路由、领域逻辑、数据访问、权限、AI 调用和共享层。
- `data/` 下的 SQLite 数据库、日志和运行数据。
- `migrations/` 下的一次性迁移与基线生成脚本。
- 数据库 schema、初始化、seed、补列和删除表逻辑。
- 会改变 API 契约、鉴权行为或持久化结构的前端提交。

## 允许修改的条件

以下条件全部满足后，后端与数据库改动才进入开发：

1. 已创建 GitHub issue 并打上 `feat` 标签，写清目标、用户价值、接口或 schema 变更、负责人、验证方式和回滚办法。
2. 若与现有宪法、契约或文档冲突，已打上 `conflict` 标签和严重程度标签。
3. 已从最新 `main` 新建独立功能分支，建议使用 `feature/<short-name>`。
4. 改动范围与 issue 一致，没有顺手重构无关模块。
5. 数据库验证使用可弃库或测试副本，不连接生产库。
6. 项目负责人参与审查，并确认相关单测、架构检查、静态检查和 e2e 结果。

## 功能分支流程

1. 在 GitHub issue 写清方案与验收条件。
2. 新建功能分支，先建立失败测试或可复现验证，再实现后端与数据库改动。
3. 保持 API 变更、数据变更和前端调用在同一功能范围内可审查。
4. 改动 schema 或内容数据时，补充恢复和兼容说明，并参考 `docs/baseline-database.md`。
5. 经审查通过后合入 `main`。未讨论、未记录或超范围的提交退回。

## 紧急问题

线上或联调阻塞时，先保留复现材料和错误日志，通知项目负责人。紧急情况仍按功能分支和验证流程处理，生产库由项目负责人操作。

## 边界判断

- 只改前端展示，不改请求或响应形状：属于前端范围。
- 需要新增字段、改状态码、改权限或改表：先讨论，再进入功能分支。
- 只是为了让页面先跑通而改后端：视为未授权的产品变更。
- 发现现有 ADR 与需求冲突：按 `adr-constitution.md` 停止并上报。

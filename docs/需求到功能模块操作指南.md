## 总览：今天的流程


分工原则：**你做裁决，AI 做起草**。你只需要回答问题、审阅产出、点头确认。

## 第 1 步：立宪 `$speckit-constitution`（一次性）

在 Codex 聊天框输入（原则作为参数直接跟在命令后）：

```
$speckit-constitution 本项目为"粤乡智匠"工匠培训平台。原则如下：
1. 技术栈红线：后端 Flask + SQLite，路由在 app.py、数据层在 database.py、
   serverless 入口 api/index.py，依赖用 uv 管理（pyproject.toml + uv.lock 权威）；
   前端 Vue3 + Vite + Pinia（frontend/）；根目录旧页面只维护不新增。
2. 规格维护模型：living spec——specs/<NNN>/spec.md 是唯一需求契约，
   需求变更先改 spec.md 再同步实现。
3. 质量门禁：TDD 红绿重构；每任务双维审查（规格合规+代码质量）；
   模块实现完成后跑 converge 对照 spec 验收。
4. 安全：.env 与任何密钥不入库；SECRET_KEY / AI_API_KEY 非演示环境必须更换。
5. 命名：路由 kebab-case、Python 函数 snake_case、提交信息中文短句祈使句。
```

**写什么**：约束、红线、质量要求、维护模型——都是"原则"。
**不写什么**：具体功能需求（那是 spec.md 的事）、当前进度（那是 NOW.md 的事）。

产出验证：
- `.specify/memory/constitution.md` 存在且包含上述 5 类
- `git add .specify && git commit -m "docs(spec): 立项目宪法"`

> 宪法第 2 条（living spec）就是待拍板的"规格维护模型"——按此模板写即视为拍板通过，想改模型现在改。

## 第 2 步：逐子系统 `$speckit-specify`

### 2.1 先拆清单（对话，不用命令）

先在聊天框让 AI 帮你把五大模块拆成子系统清单（这一步是普通对话）：

```
帮我把以下五大模块拆成可独立交付、可独立验收的子系统清单，
每个子系统给出：名称、一句话职责、主要用户角色。
模块：〈在这里贴你的五大模块〉
```

拆分判据：**能独立说清用户故事 + 能独立验收 = 一个子系统**。
- 反例："用户管理"太大（拆成登录认证 / 角色管理 / 权限控制）
- 反例："一个按钮"太小（并入所属子系统）

确认清单后，每个子系统获得编号（001、002、003……）。

### 2.2 逐个 specify（一次一个）

在 Codex 聊天框输入需求描述，套用模板：

```
$speckit-specify 构建学员学习模块：学员登录后可按课程查看章节列表、
进入章节学习页、标记章节完成进度。

用户故事：
1) 作为学员，我想查看我的课程列表，以便选择学习内容
2) 作为学员，我想进入章节学习页，以便按顺序学习
3) 作为学员，我想标记章节完成，以便追踪学习进度

边界：不含考试与证书（后续独立模块）；不含教师端功能。

验收标准：
- 课程列表加载 < 1 秒
- 进度标记即时生效并持久化（刷新后不丢）
```

**要点**：
- 说 **WHAT / WHY**（业务目标、用户故事、边界、验收），不要说 **HOW**（表结构、API 路由——那是实现计划的事）
- **边界（不含什么）必须写**——这是防 AI 自行扩大范围最有效的一句
- AI 会自动：建同名分支 `NNN-<slug>` → 建 `specs/NNN-<slug>/spec.md` → 起草完整规格

产出验证：
- `git branch` 出现同名 feature 分支
- `specs/001-xxx/spec.md` 存在，含用户故事、边界、验收标准

### 2.3 子系统之间的依赖

如果子系统 A 依赖 B（如"进度标记"依赖"登录认证"），在需求描述里写明：
```
依赖：依赖 001-登录认证 提供的会话（见 specs/001-登录认证/spec.md）
```
spec-kit 会在 analyze 时检查这种引用的一致性。

## 第 3 步：`$speckit-clarify`（有歧义才跑）

```
$speckit-clarify
```

AI 会提**最多 5 个高影响问题**，逐个回答（不要一次糊一坨），答案自动写回 spec.md。

跳过判据：如果 spec 里每个功能点你都能答上"对谁、什么场景、怎么算完成"，直接跳过。

---

## 第 4 步：`$speckit-checklist` + `$speckit-analyze`

```
$speckit-checklist
$speckit-analyze
```

- checklist 生成 `specs/NNN-xxx/checklists/requirements.md`（质量检查表）
- analyze 报告缺口与不一致

对报告的**裁决权在你**：接受 → 让 AI 修补 spec；不接受 → 说明理由让 AI 忽略该项。

---

## 第 5 步：冻结 = 提交

你通读 `specs/NNN-xxx/spec.md` 确认无误后：

```bash
git add specs/ .specify/ .agents/ AGENTS.md .gitignore
git commit -m "docs(spec): 冻结 001-xxx 功能模块需求"
```

**提交即冻结**。此后所有实现都对照这份 spec；需求变更 = 改 spec.md 重新 analyze（living spec 回路）。

## 常见坑

1. **需求变更不要在对话里口头说**——改 spec.md（或重新 specify），文件是唯一权威源，口头说的下个会话就丢
2. **clarify 的问题不要含糊回答**——每个答案都会固化进 spec，事后改成本更高
3. **宪法别频繁改**——它是原则层，改动影响所有 feature
4. **不要跳过冻结直接开写**——spec 没提交 = 没有验收基准，converge 无从对照
5. **命令没反应** → 确认在项目根目录启动的 Codex；技能名带 `$` 前缀；重启会话再试

# Feature Specification: 系统管理后台

**Feature Branch**: `v2/lixKRT/011-admin-console`

**Created**: 2026-09-20

**Status**: Frozen

**Input**: User description: "admin-console: 系统管理后台子系统。超级管理员负责全量看板、账号与权限、积分规则和全平台数据管理；普通管理员负责内容审核、评论监管、举报与反馈、预置内容、奖品与履约及内容运维看板。11 是内容审核、积分规则、奖品库、履约管理、预置内容、AI 学伴功能说明知识库和全平台统计的关键提供者。"

## Clarifications

### Session 2026-09-20

- Q: 三类先审后发内容是否在一个统一队列中按 `content_type` 分列展示？ → A: 使用一个统一审核队列，按 `course_video`、`job_position`、`handcraft_teaching_video` 分列/筛选，并分别显示待审核数量；三类共用相同审核动作和通知结果语义。
- Q: 驳回意见的长度与必填规则是什么？ → A: 驳回意见去除首尾空白后必填，长度为 1 至 500 个字符；空值、纯空白或超长均拒绝，不改变审核状态。
- Q: 05 尚不具备 `rejected -> pending` 和首次 `submit_for_review`，11 应补实现还是标记为 05 待办？ → A: 11 不修改 05，也不伪造能力。11 的通用审核真实现完整支持课程视频和职位；05 专用适配器只映射 05 已具备的读取、通过、驳回和允许状态下的编辑动作。首次提交及 `rejected -> pending` 保持为 05 的待办，适配器遇到这些动作必须抛出 `ProviderConflictError` 或 `ProviderUnavailableError`。
- Q: 离散训练行为权重如何与 05 的 `training_weights` 对接？ → A: 固定支持 `default`、`live_script`、`simulation`、`copy_training`、`customer_service` 五个键；前四个业务键和 `default` 均映射到 05 已有字段，未配置的具体训练类型回退到 `default`，不得创建第二套权重字段。
- Q: 六类预置内容应采用统一字段还是保留各自数据形态？ → A: 保留各内容类型自身的数据形态和编辑粒度，由统一管理目录提供分类、稳定 ID、状态和排序；农产品、农时日历、病虫害知识库、非遗技艺、成功案例和功能说明知识条目分别校验其领域字段。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 超级管理员全量看板 (Priority: P1)

超级管理员打开管理后台后，可在一个全量看板中查看用户、岗位、课程、政策/新闻、三类待审核内容、积分发放、兑换和待发放履约等平台级指标。

**Why this priority**: 看板是超管掌握平台状态和进入各项管理动作的总入口，也是跨模块统计口径是否一致的第一验收点。

**Independent Test**: 构造六类账户、已上架/未上架课程和岗位、政策/新闻浏览、三类待审核内容、积分流水、兑换和履约数据，逐项核对超管看板数值与来源模块一致。

**Acceptance Scenarios**:

1. **Given** 平台存在六类角色的启用和禁用账户，**When** 超管打开全量看板，**Then** 总用户数按角色分类，学员数单独显示，禁用账户按明确口径纳入总数。
2. **Given** 课程和岗位分别存在已上架、未上架和已删除记录，**When** 超管打开全量看板，**Then** 岗位数只统计已审核、未删除且已发布的岗位，课程数只统计当前已上架课程。
3. **Given** 三类先审后发内容分别存在待审核记录，**When** 超管打开全量看板，**Then** 三类待审核数分列且与统一审核队列一致。
4. **Given** 存在积分发放流水、兑换记录和待发放履约单，**When** 超管打开全量看板，**Then** 展示积分发放总量、兑换笔数和待发放履约数。

### User Story 2 - 账号与权限管理 (Priority: P1)

超级管理员按角色和关键词查询账户，查看详情，创建企业、政府、普通管理员和超级管理员账户，禁用或启用账户，并重置用户密码。普通管理员不能进入账号管理或执行任何账号写操作。

**Why this priority**: 账户状态直接控制登录和数据访问，是所有后台权限边界的上游。

**Independent Test**: 分别以超管和普管登录，验证创建、筛选、详情、禁用、启用、重置密码、通知和越权拒绝；验证账户不存在物理删除入口。

**Acceptance Scenarios**:

1. **Given** 超管已登录，**When** 按角色和关键词筛选账户，**Then** 列表只返回匹配账户并显示用户名、姓名、角色、启用状态和创建时间。
2. **Given** 超管创建企业、政府、普管或超管账户，**When** 提交有效用户名、姓名和初始密码，**Then** 创建成功且新账户可登录，其他角色不可自助注册这些账户。
3. **Given** 账户当前可用，**When** 超管禁用账户，**Then** 该用户下一次登录或受保护操作立即被拒绝，已有业务数据保留。
4. **Given** 账户当前被禁用，**When** 超管启用或重置密码，**Then** 恢复状态或写入新密码哈希；重置结果通过 02 通知用户，不暴露明文密码给无关人员。
5. **Given** 普管已登录，**When** 尝试访问账号列表、创建、禁用、启用或重置密码，**Then** 全部拒绝，且不泄露账户存在性。

### User Story 3 - 三类内容统一审核 (Priority: P1)

普通管理员在统一审核队列中按内容类型处理课程视频、职位和非遗教学视频，通过后内容立即进入对应学员可见位置，驳回时填写意见并经 02 通知提交者。

**Why this priority**: 11 是跨模块审核槽的唯一生产者，审核真实现是 08、09 和 05 适配器可落地的前置条件。

**Independent Test**: 使用 11 的通用审核 provider 驱动课程和职位完整状态机；使用 05 兼容适配器驱动其现有视频能力；逐项核对版本冲突、可见性、驳回意见和通知。

**Acceptance Scenarios**:

1. **Given** 三类内容均存在待审核记录，**When** 普管打开统一审核队列，**Then** 队列按 `content_type` 分列/筛选并分别显示三类待审核数量。
2. **Given** 待审核内容版本有效，**When** 普管通过审核，**Then** 状态变为 `approved`、`published_at` 非空、学员端即时可见，并产生一次审核通过通知。
3. **Given** 待审核内容版本有效，**When** 普管提交 1 至 500 字的驳回意见，**Then** 状态变为 `rejected`、意见保存、发布时间清空、学员端不可见，并经 02 通知提交者。
4. **Given** 内容状态为 `rejected`，**When** 08/09 内容修改后重新提交，**Then** 状态回到 `pending` 并清除旧意见；05 适配器在 05 尚未支持该转换时返回明确冲突。
5. **Given** 审核请求携带旧版本或非法状态转换，**When** 提交审核，**Then** 拒绝覆盖新状态，且不产生重复通知。

### User Story 4 - 奖品库与履约管理 (Priority: P1)

普通管理员维护奖品名称、积分成本和库存，控制上架/下架，并处理待发放、已发放和已核销履约单。取消待发放履约时，系统原子回退积分、回滚库存并经 02 通知学员。

**Why this priority**: 奖品与履约是积分体系的最终兑付路径，任何不一致都会造成积分或库存损失。

**Independent Test**: 构造多奖品、多库存、多状态兑换和履约数据，验证上下架同步、发放、取消、核销、完整用户上下文、积分回退、库存回滚和通知幂等。

**Acceptance Scenarios**:

1. **Given** 普管已登录，**When** 创建或编辑奖品名称、积分成本和库存，**Then** 有效配置保存并立即影响学员端可兑换状态。
2. **Given** 奖品已上架，**When** 普管下架，**Then** 学员端立即不可兑换但历史兑换和履约保留；重新上架后按当前库存恢复可见。
3. **Given** 履约单状态为待发放，**When** 普管执行发放，**Then** 状态变为已发放并经 02 通知学员。
4. **Given** 履约单状态为待发放，**When** 普管取消，**Then** 在单一业务边界内恢复兑换所扣积分、回滚预留库存、状态变为已取消并经 02 通知学员。
5. **Given** 履约单状态为已发放，**When** 普管或学员完成核销，**Then** 状态变为已核销且不重复发放或回退积分。
6. **Given** 普管查看履约上下文，**When** 打开相关用户详情，**Then** 可查看身份、联系方式、积分流水和完整兑换记录，但不能进入账号管理或积分规则配置。

### User Story 5 - 积分规则配置 (Priority: P2)

超级管理员配置学习时长折算比率、离散训练行为权重、每日获取上限和积分有效期。保存后学员端下一次积分计算立即使用新规则，有效期变化不追溯已发积分。

**Why this priority**: 积分规则是跨模块平台规则，但依赖 05 已有积分账本与事件处理能力。

**Independent Test**: 修改每个规则字段，验证 05 的下一次积分计算、每日上限、自然年到期和永久规则；验证旧积分到期时间不被追溯改写。

**Acceptance Scenarios**:

1. **Given** 超管修改时长折算比率或每日上限，**When** 学员产生下一次有效学习行为，**Then** 使用新规则计算并受新每日上限约束。
2. **Given** 超管修改四个离散训练行为权重或默认权重，**When** 对应训练行为产生积分事件，**Then** 使用匹配权重；未配置的具体类型使用 `default`。
3. **Given** 有效期从永久改为按自然年，**When** 保存规则，**Then** 仅此后新发放积分按自然年到期，已发积分保留原到期结果。
4. **Given** 规则字段非法、版本冲突或保存失败，**When** 提交，**Then** 原规则保持生效，学员端不得出现半更新状态。
5. **Given** 普管已登录，**When** 尝试读取或修改积分规则配置，**Then** 写操作全部拒绝。

---

### User Story 6 - 六类预置内容维护 (Priority: P2)

普通管理员维护农产品目录、农时日历、病虫害知识库、非遗技艺内容、成功案例和 AI 学伴功能说明知识库，增删改后对应消费模块下一次读取立即生效。

**Why this priority**: 预置内容支撑 03、05、06 和未来 12，是跨模块只读来源的权威维护面。

**Independent Test**: 对六类内容分别创建、编辑、删除，并分别通过 03、05、06 和 12 provider 契约读取，验证即时生效、稳定 ID 和历史引用语义。

**Acceptance Scenarios**:

1. **Given** 普管创建或编辑农产品、农时日历或病虫害知识条目，**When** 03 下一次读取，**Then** 返回最新内容且稳定 ID 不变。
2. **Given** 普管编辑非遗技艺介绍、步骤或材料指南，**When** 05 下一次读取，**Then** 完整技艺内容更新；有效步骤不足六步时标记不可学习而不是发布残缺内容。
3. **Given** 普管编辑成功案例，**When** 06 下一次读取，**Then** 列表和详情即时反映更新。
4. **Given** 普管维护 AI 学伴功能说明知识条目，**When** 12 通过知识库 provider 读取，**Then** 可获取启停状态、稳定 ID、标题、正文、适用功能、跳转目标和更新时间。
5. **Given** 被历史记录引用的预置内容被删除或下架，**When** 历史记录读取，**Then** 稳定 ID 仍可解析或明确标记来源不可用，不得静默替换为其他内容。

### User Story 7 - 评论监管、举报处理与意见反馈 (Priority: P2)

普通管理员巡查评论、静默删除违规评论，处理学员举报并查看意见反馈。举报确认或驳回都记录处理结果，处理量进入普管看板。

**Why this priority**: 评论即时发布，需要后台事后监管闭环；现有共享评论模型可复用，但举报和反馈持久化尚缺失。

**Independent Test**: 构造可见评论、举报和反馈，验证静默删除、确认举报、驳回举报、处理结果、看板计数和越权边界。

**Acceptance Scenarios**:

1. **Given** 评论当前可见，**When** 普管删除违规评论，**Then** 学员端下一次读取立即不再显示，不向被删者发送通知，并保留可审计处理记录。
2. **Given** 举报记录处于待处理，**When** 普管确认违规，**Then** 评论被静默删除、举报状态记录为确认违规并增加处理量。
3. **Given** 举报记录处于待处理，**When** 普管驳回举报，**Then** 评论保留、举报状态记录为驳回并增加处理量。
4. **Given** 学员意见反馈已通过 07 或 12 的提交入口进入 11 的反馈接收契约，**When** 普管打开反馈列表，**Then** 可查看内容、提交者、时间、状态和处理结果。
5. **Given** 普管处理举报或反馈，**When** 打开内容运维看板，**Then** 处理量按已处理记录计入且不包含用户统计。

### User Story 8 - 全平台数据管理 (Priority: P2)

超级管理员查看、纠错、编辑、下架或删除跨模块业务数据，包括政策/新闻、课程、职位、非遗教学视频、评论和预置内容。

**Why this priority**: 超管需要最终纠错能力，但不得取代教师、企业、政府或普管的日常生产职责。

**Independent Test**: 对每类数据执行允许和禁止动作，验证状态机、可见性、历史保留、审计和权限拒绝。

**Acceptance Scenarios**:

1. **Given** 政府已发布政策或新闻，**When** 超管执行纠错，**Then** 可修正明确错误；不得改变原作者、创建来源或把普通编辑扩展为政府发布流程。
2. **Given** 已上架课程，**When** 超管下架，**Then** 学员端立即不可见，学习进度、测验成绩和学习成果保留；删除时采用可审计隐藏语义，不级联删除历史学习数据。
3. **Given** 已通过职位，**When** 超管下架或删除，**Then** 学员端和岗位 provider 立即不可见；申请、简历快照、沟通关系和状态历史保留。
4. **Given** 已通过非遗教学视频，**When** 超管下架，**Then** 05 不再向学员提供播放；删除时历史学习成果仍可读取并标记来源不可用。
5. **Given** 评论或预置内容被删除，**When** 读取历史或审计记录，**Then** 处理结果可追踪，不得无记录地物理丢失。

---

### User Story 9 - 兑换记录与完整用户上下文查询 (Priority: P2)

超级管理员和普通管理员可查询完整兑换记录。普管只能在兑换与履约上下文查看相关用户详情、联系方式和完整积分流水。

**Why this priority**: 履约处理需要足够上下文，但用户数据权限必须严格限定在业务目的内。

**Independent Test**: 以超管和普管分别查询同一兑换，核对记录、用户字段、联系方式和积分流水；以无关用户或账号管理入口验证越权拒绝。

**Acceptance Scenarios**:

1. **Given** 存在兑换记录，**When** 超管或普管打开兑换详情，**Then** 显示用户身份、联系方式、奖品快照、积分成本、兑换状态、履约状态和完整积分流水。
2. **Given** 普管在履约列表查看相关用户，**When** 打开详情，**Then** 仅可读取履约所需用户上下文，不显示或开放账号状态、密码重置和积分规则操作。
3. **Given** 普管尝试通过兑换上下文修改账号或规则，**When** 提交请求，**Then** 拒绝且不改变数据。
4. **Given** 超管执行全平台数据查询，**When** 读取兑换记录，**Then** 可按用户、奖品、兑换状态和时间筛选并保持确定排序。

---

### User Story 10 - 普通管理员内容运维看板 (Priority: P3)

普通管理员打开只包含内容运维指标的看板，不展示任何用户统计或培训类指标。

**Why this priority**: 看板为内容运营提供摘要，但权限隔离必须优先于指标丰富度。

**Independent Test**: 构造用户、学习行为和内容处理数据，序列化看板响应并断言禁止键全部不存在；核对内容指标与各自来源一致。

**Acceptance Scenarios**:

1. **Given** 三类内容分别存在待审核记录，**When** 普管打开看板，**Then** 三类待审核数分列。
2. **Given** 课程和岗位状态变化，**When** 普管打开看板，**Then** 已上架课程数和在架职位数反映最新状态。
3. **Given** 评论、举报和反馈处理数据存在，**When** 普管打开看板，**Then** 显示评论/举报处理量和反馈处理量。
4. **Given** 奖品和履约数据存在，**When** 普管打开看板，**Then** 显示奖品库存与待发放履约数。
5. **Given** 平台存在用户、学习进度和测验数据，**When** 普管打开看板，**Then** 响应中不得出现总用户、角色分布、学员明细、培训进度、完成率或测验统计键。

### Edge Cases

- 同一次审核决定被重复提交时，必须保持幂等，不重复变更状态或发送重复通知。
- 旧版本审核请求、并发编辑、并发下架、并发删除和并发履约动作只允许一个线性结果，其余请求返回冲突。
- 审核 provider、02 通知或数据来源不可用时，业务状态不得出现半提交；通知投递失败不得回滚已提交的审核状态。
- 驳回意见为空、纯空白或超过 500 字时，不改变内容状态。
- 创建账户用户名重复、密码不足 8 位、角色非法或尝试物理删除账户时，请求拒绝。
- 禁用账户已有会话时，下一次受保护操作必须被拒绝，不能等会话自然过期。
- 积分规则保存失败时必须继续使用上一个有效版本；没有有效规则和快照时返回明确不可用，不得暂停或伪造积分。
- 有效期变更不得回写或重算已发积分；自然年清零必须幂等，02 通知失败可重试但不重复扣减。
- 取消履约时积分流水缺失、库存预留缺失或并发状态已变化，必须整体失败并保留可重试状态，不得只回退一项。
- 奖品下架不删除历史兑换；库存不得低于已被待发放履约预留的数量。
- 评论删除不得通知被删者；举报确认和驳回必须各自留下处理结果。
- 预置内容被历史引用后删除时，历史记录保留稳定 ID 或显示来源不可用，不得把引用重定向到其他内容。
- 政策/新闻纠错不得改变发布状态或重复触发政策订阅推送，除非政府模块显式发起新的发布事件。
- 普管看板的禁止键必须递归检查，不能只隐藏页面控件而仍在响应中返回用户数据。
- 05 视频适配器收到首次提交或 `rejected -> pending` 时不得创建记录、伪造状态或绕过 05 状态机。

## Requirements *(mandatory)*

### Functional Requirements

#### 角色、入口与审计

- **FR-001**: 系统 MUST 只允许 `super_admin` 和 `admin` 进入管理后台；`super_admin` 拥有全平台管理和纠错权限，`admin` 只拥有内容运维权限。
- **FR-002**: 系统 MUST 复用 01 的账户、会话、角色和禁用账户拦截，不得创建第二套登录、会话或角色注册表。
- **FR-003**: 所有管理动作 MUST 从 01 会话覆盖操作者身份和角色，客户端提交的角色、用户 ID 或审核者 ID 不构成授权依据。
- **FR-004**: 管理后台 MUST 记录账户状态、密码重置、积分规则、审核决定、内容下架/删除、评论/举报处理、预置内容变更、奖品和履约动作的操作者、时间、目标与结果。
- **FR-005**: 普通管理员 MUST NOT 访问账号管理、账户状态、密码重置、积分规则配置、用户全量统计或培训类指标。
- **FR-006**: 普通管理员 MAY 仅在兑换和履约上下文中查看相关用户身份、联系方式和完整积分流水；该权限不得扩展为全局用户搜索或账号管理。

#### 超级管理员全量看板

- **FR-007**: 全量看板 MUST 展示按角色分类的总用户数和单独的学员数，并明确是否包含禁用账户；口径为全部已创建账户，禁用账户计入总数。
- **FR-008**: 全量看板 MUST 展示岗位数，口径为已审核通过、未删除且已发布的全平台岗位。
- **FR-009**: 全量看板 MUST 展示课程数，口径为当前已上架的全平台课程。
- **FR-010**: 全量看板 MUST 展示政策总数、新闻总数及各自累计浏览量；已删除政策/新闻不计入总数和浏览量。
- **FR-011**: 全量看板 MUST 分列 `course_video`、`job_position`、`handcraft_teaching_video` 三类待审核数。
- **FR-012**: 全量看板 MUST 展示积分发放总量、兑换笔数和待发放履约数。
- **FR-013**: 任一来源不可用时，看板 MUST 返回明确不可用标记，不得用伪造的零值冒充真实数据。

#### 账号与权限管理

- **FR-014**: 超级管理员 MUST 能按角色筛选并按用户名或姓名关键词搜索账户。
- **FR-015**: 账户列表 MUST 至少显示稳定用户 ID、用户名、姓名、角色、启用状态、创建时间和更新时间；不得返回密码哈希或明文密码。
- **FR-016**: 超级管理员 MUST 能创建 `enterprise`、`government`、`admin`、`super_admin` 四类账户，并分配用户名、姓名和初始密码。
- **FR-017**: 企业、政府、普通管理员和超级管理员 MUST NOT 通过公开注册创建；公开注册仍只允许 01 已定义的学员和教师。
- **FR-018**: 超级管理员 MUST 能禁用和启用账户；禁用后下一次登录或受保护操作立即拒绝，业务数据不删除。
- **FR-019**: 超级管理员 MUST 能重置用户密码为符合 01 密码规则的初始密码，并只保存密码哈希。
- **FR-020**: 密码重置结果 MUST 经 02 通知用户或通过明确的线下交付状态记录；不得把明文密码发送给无关人员。
- **FR-021**: 系统 MUST NOT 提供账户物理删除能力。
- **FR-022**: 系统 MUST 预置且只预置一个可识别的首个超级管理员账户；初始化不得重复创建或覆盖已有超管密码。

#### 积分规则配置

- **FR-023**: 超级管理员 MUST 能配置 `seconds_per_point`，其值为正整数。
- **FR-024**: 超级管理员 MUST 能配置 `training_weights`，且必须包含 `default`；允许的业务键固定为 `live_script`、`simulation`、`copy_training`、`customer_service`，所有值均为正整数。
- **FR-025**: 未配置的具体训练行为 MUST 回退到 `training_weights.default`；系统 MUST NOT 建立第二套离散行为权重字段。
- **FR-026**: 超级管理员 MUST 能配置正整数 `daily_limit`，按 `Asia/Shanghai` 自然日执行。
- **FR-027**: 超级管理员 MUST 能在 `permanent` 和 `natural_year` 之间配置 `expiry_mode`。
- **FR-028**: 积分规则保存成功后，学员端下一次积分计算 MUST 使用新规则，不得要求重启服务或重新登录。
- **FR-029**: 有效期变更 MUST NOT 追溯修改已发积分、历史流水或原到期时间。
- **FR-030**: 积分规则 MUST 通过 `handcraft_points_policy_provider` 的 `PointsPolicyProvider.get_policy()` 提供给 05，返回字段必须与 05 现有 `_normalize_policy()` 对齐。
- **FR-031**: 规则版本变化 MUST 具有稳定 `version`；保存失败或并发冲突不得产生部分更新。
- **FR-032**: 规则来源不可用时，05 MAY 使用最近有效快照；没有快照时必须返回明确不可用，不得暂停积分或使用伪造默认值。

#### 全平台数据管理

- **FR-033**: 超级管理员 MUST 能查看各业务模块的稳定 ID、归属、状态、版本、创建/更新时间和当前可见性。
- **FR-034**: 政策/新闻的常规编辑、发布和撤回仍归政府；超级管理员只保留纠错和必要的下架/删除能力，纠错不得重复触发政策订阅推送。
- **FR-035**: 课程下架 MUST 立即从学员课程区块、聚合页和推荐池移除，并保留进度、测验记录和学习成果。
- **FR-036**: 课程删除 MUST 采用可审计隐藏语义，不物理级联删除课程历史、学习进度或测验结果。
- **FR-037**: 职位下架或删除 MUST 立即从企业当前职位列表和学员岗位 provider 移除；申请、快照、状态历史和沟通关系保留。
- **FR-038**: 非遗教学视频下架 MUST 使 05 不再提供学员播放；删除 MUST 保留历史学习成果并标记来源不可用。
- **FR-039**: 评论删除 MUST 使用静默隐藏或可审计删除语义，学员端不再返回，处理结果仍可审计。
- **FR-040**: 预置内容下架 MUST 使其从对应消费模块隐藏；删除 MUST 保持稳定 ID 的历史可解析性或明确来源不可用。
- **FR-041**: 每类内容的删除动作 MUST 遵循其模块状态机，不得用一个统一数据库级联删除绕过课程、职位、审核、积分或履约约束。
- **FR-042**: 并发编辑、审核、下架或删除 MUST 使用版本或等价乐观并发控制，旧写入不得覆盖新状态。

#### 兑换记录查询

- **FR-043**: 超管和普管 MUST 能查询兑换记录及履约状态。
- **FR-044**: 兑换详情 MUST 至少包含兑换 ID、用户 ID、用户身份、联系方式、奖品快照、积分成本、请求 ID、兑换状态、库存预留状态、履约状态和时间字段。
- **FR-045**: 兑换详情 MUST 提供该用户的完整积分流水，包含交易类型、来源模块、来源事件、金额、余额影响和时间。
- **FR-046**: 兑换列表 MUST 支持用户、奖品、兑换状态、履约状态和时间范围筛选，并以创建时间倒序、稳定 ID 正序为默认排序。
- **FR-047**: 普管的兑换查询权限 MUST 只通过履约相关上下文暴露，不得增加全局用户搜索能力。

#### 内容审核

- **FR-048**: 系统 MUST 提供唯一 `content_review_provider` 真实现，完整实现 `ContentReviewProvider`。
- **FR-049**: 统一审核队列 MUST 支持 `course_video`、`job_position`、`handcraft_teaching_video` 三种 `content_type` 的分列/筛选和计数。
- **FR-050**: `submit_for_review` MUST 只接受内容模块已持久化、已有稳定 `content_id` 和当前 `expected_version` 的记录，不得创建业务内容。
- **FR-051**: 首次提交、待审核编辑、通过后编辑、驳回后重提 MUST 遵循冻结状态机：

```text
pending -> approved
pending -> rejected
pending -> pending
approved -> pending
rejected -> pending
```

- **FR-052**: `pending` 内容对学员不可见；`approved` 内容在 `published_at` 非空时可见；`rejected` 内容不可见。
- **FR-053**: 有实际字段变化时版本 MUST 前进；无实际变化提交 MUST 返回原状态和原版本，不创建新审核轮次。
- **FR-054**: `approved` 编辑后 MUST 回到 `pending` 并清除 `published_at`。
- **FR-055**: `rejected` 修改后 MUST 回到 `pending` 并清除旧驳回意见。
- **FR-056**: 审核通过 MUST 写入非空 `published_at` 并清空旧驳回意见。
- **FR-057**: 驳回意见 MUST 去除首尾空白后非空，长度为 1 至 500 个字符。
- **FR-058**: `approve`、`reject`、`edit`、`submit` MUST 使用 `expected_version` 防止旧写入覆盖新写入。
- **FR-059**: 版本冲突、非法状态转换或不支持的动作 MUST 抛出 `ProviderConflictError`；来源未实现 MUST 抛出 `ProviderUnavailableError`。
- **FR-060**: 审核结果通知 MUST 调用 02 的 `emit_review_result(event_id, submitter_id, content_type, content_id, approved, opinion)` 或字段完全等价的接收契约。
- **FR-061**: 状态转换与通知 outbox 写入 MUST 处于同一业务提交边界；通知投递失败不得回滚审核状态。
- **FR-062**: 08、09、05 和 11 适配器 MUST NOT 为同一审核结果重复发送通知。

#### 05 非遗视频专用适配器

- **FR-063**: 11 MUST 提供 05 视频专用 `ContentReviewProvider` 适配器，但 MUST NOT 修改 05 已合并的审核 action 代码。
- **FR-064**: 适配器 MUST 将 `get_review_status` 映射到 05 的视频读取结果，并把 05 `status`/`published` 规范化为通用 `review_status`。
- **FR-065**: 适配器 MUST 将 `approve` 和 `reject` 映射为 05 的 `apply(action="approve"/"reject")`，并传递 `video_id`、`version`、`submitter_id`、`reviewer_role` 和驳回意见。
- **FR-066**: 适配器 MUST 将 `edit` 映射为 05 的 `apply(action="edit")`，并只允许 05 当前支持的状态和教师所有权。
- **FR-067**: 通用 `expected_version` MUST 映射到 05 `version`；05 返回的 `status`、`version`、发布时间、驳回意见和时间字段 MUST 映射为通用审核记录。
- **FR-068**: `submit_for_review` 只可映射到 05 已存在且状态允许 `edit` 的记录；05 尚未支持首次提交和 `rejected -> pending` 时，适配器 MUST 返回明确冲突或不可用，不得创建记录或伪造状态。
- **FR-069**: 适配器 MUST 由 11 从 01 会话覆盖 `reviewer_id` 和 `reviewer_role`，并保留可审计信息；客户端传入值不构成授权。
- **FR-070**: 适配器 MUST 保留 05 的 `handcraft_teaching_video` 通知类型和既有 outbox 行为，不得重复通知。

#### 评论监管、举报与反馈

- **FR-071**: 学员评论经目标内容和正文校验后 MUST 即时发布，不进入先审后发队列；普通管理员 MUST 能按内容类型、内容 ID、作者、时间和可见状态巡查课程视频及非遗教学视频评论。
- **FR-072**: 普通管理员删除违规评论时 MUST 静默执行：学员端不再展示，不通知被删评论者，但保留处理记录。
- **FR-073**: 系统 MUST 持久化举报记录，至少包含举报 ID、评论 ID、举报人、理由、状态、处理人、处理时间、处理结果和创建时间。
- **FR-074**: 确认举报违规时，系统 MUST 静默删除或隐藏评论、记录确认结果，并只计一次处理量。
- **FR-075**: 驳回举报时，系统 MUST 保留评论、记录驳回结果，并只计一次处理量。
- **FR-076**: 举报重复处理 MUST 幂等，不得改变最终处理结果或重复计数。
- **FR-077**: 系统 MUST 定义意见反馈接收契约，供 07 或 12 的提交入口调用；11 MUST 提供普管反馈列表、详情和状态处理能力。
- **FR-078**: 意见反馈记录 MUST 至少包含反馈 ID、提交者、内容、提交时间、状态、处理人、处理结果和更新时间。
- **FR-079**: 评论、举报和反馈处理量 MUST 进入普管内容运维看板，但不得携带用户统计。

#### 预置内容维护

- **FR-080**: 系统 MUST 提供六类预置内容的管理能力：农产品目录、农时日历、病虫害知识库、非遗技艺内容、成功案例、AI 学伴功能说明知识库。
- **FR-081**: 农产品条目 MUST 至少包含稳定产品键、名称、排序和启停状态，并保持 03 现有 `PresetContentProvider` 字段兼容。
- **FR-082**: 农时日历条目 MUST 至少包含产品键、月份、农事任务、管理要点、节气和当月提示，并保持 03 现有读取字段兼容。
- **FR-083**: 病虫害知识条目 MUST 至少包含稳定 ID、排序、病虫害名称、适用产品、症状、别名、答案和启停状态，并保持 03 现有本地降级检索字段兼容。
- **FR-084**: 非遗技艺内容 MUST 至少包含稳定技艺键、名称、介绍、步骤、材料指南、排序、来源可用性和启停状态；完整可学习技艺必须满足 05 已有步骤完整性规则。
- **FR-085**: 成功案例 MUST 至少包含稳定案例 ID、标题、摘要、背景、历程、经验启示、排序、发布时间、更新时间和启停状态，并保持 06 现有读取字段兼容。
- **FR-086**: AI 学伴功能说明知识条目 MUST 至少包含稳定知识 ID、标题、正文、适用功能、跳转目标、启停状态、版本和更新时间。
- **FR-087**: 六类预置内容 MUST 分别校验其领域字段，不得用单一宽松 JSON 绕过类型约束。
- **FR-088**: 预置内容保存或删除后，对应消费模块下一次读取 MUST 立即反映；稳定 ID 不得因编辑改变。
- **FR-089**: 删除被历史引用的预置内容时 MUST 保留稳定 ID 可解析性或明确来源不可用，不得级联删除历史学习成果、积分或履约记录。

#### 奖品库与履约管理

- **FR-090**: 普通管理员 MUST 能创建、查看、编辑奖品名称、积分成本和库存。
- **FR-091**: 奖品配置 MUST 通过 `handcraft_reward_catalog_provider` 的 `RewardCatalogProvider.list_rewards()` 提供给 05；下架或库存变化后学员端下一次读取立即生效。
- **FR-092**: 奖品上架状态 MUST 与 `is_online`/`source_available` 语义兼容；下架不得删除历史兑换和履约。
- **FR-093**: 库存 MUST 不得小于待发放履约已预留数量；库存编辑必须使用并发保护。
- **FR-094**: 普通管理员 MUST 能按状态、用户、奖品和时间查询履约队列。
- **FR-095**: 履约状态机 MUST 支持 `pending -> issued -> verified` 和 `pending -> canceled`，终态不得再次转换。
- **FR-096**: 发放待发放履约 MUST 经 02 通知学员，重复请求不得重复发放或重复通知。
- **FR-097**: 取消待发放履约 MUST 在同一业务边界内完成积分回退、库存回滚、兑换与履约状态更新及通知 outbox 写入。
- **FR-098**: 核销 MUST 支持学员确认收货或管理员核销，并只允许从已发放状态进入已核销。
- **FR-099**: 履约管理 MUST 复用 05 现有 `FulfillmentAdminActionProvider.apply()` 领域动作；11 可增加查询和上下文，但不得复制第二套积分、库存或履约状态机。
- **FR-100**: 履约动作的结果 MUST 通过 02 既有履约通知事件投递；通知失败可重试但不得回滚已提交的业务状态。

| 系统公告 | 可创建、查看、发布 | 不可见、不可操作 | 普管请求拒绝；02 群发事件不重复 |
| 政策/新闻 | 纠错、下架/删除 | 不可见、不可操作 | 普管请求拒绝；超管纠错不触发重复订阅推送 |
| 课程、职位、非遗视频常规生产 | 纠错/管理，不代替生产者 | 仅审核/监管 | 普管不能创建课程、职位或政府内容 |

#### 普通管理员看板排除项

- **FR-101**: 普管看板 MUST 只包含三类待审核数、已上架课程数、在架职位数、评论处理量、举报处理量、反馈处理量、奖品库存和待发放履约数。
- **FR-102**: 普管看板 MUST 递归排除以下键或等价字段：`total_users`、`role_distribution`、`student_total`、`student_count`、`user_details`、`average_progress`、`completion_rate`、`quiz_attempt_count`、`quiz_average_score`、`training_progress`、`learning_behavior_count`。
- **FR-103**: 普管看板排除断言 MUST 对完整 JSON 响应执行递归键扫描，不能只断言页面隐藏或顶层字段不存在。

#### Provider 注册与错误规则

- **FR-104**: 每个新增 provider MUST 提供唯一 `set_<provider_key>_provider(app, provider)` 和 `get_<provider_key>_provider()`；`get` 在未注册时返回协议完整的占位实现。
- **FR-105**: 11 MAY 提供 `configure_admin_providers()` 便利入口，但 MUST 只委托上述唯一 `set_*` 槽，不得建立第二注册表。
- **FR-106**: 新增 provider 错误 MUST 使用 `ProviderValidationError`、`ProviderNotFoundError`、`ProviderConflictError`、`ProviderUnavailableError`、`ProviderAccessDeniedError` 的 `code/message/details` 形状。
- **FR-107**: 列表返回 MUST 使用确定排序和稳定 ID tie-breaker；只有 spec 明确授权时才使用 cursor 分页。
- **FR-108**: 时间字段 MUST 使用带时区 ISO 8601；新 provider 规范使用 `+08:00`，旧来源时间由适配器规范化。
- **FR-109**: provider 落地后 MUST 只替换注册槽，03、05、06、08、09、12 不得按具体实现类型分叉。
- **FR-110**: 11 MUST NOT 发明 010 当前不消费的伪统计槽；全平台统计先作为 11 内部读取服务实现。若 010 后续需要，先更新 010 消费 spec 再新增 provider。

#### 通知与失败处理

- **FR-111**: 审核结果、密码重置、履约发放和履约取消 MUST 经 02 投递，不得建立第二套消息中心。
- **FR-112**: 通知事件 MUST 使用稳定 `event_id` 幂等；重复业务请求不得产生重复用户可见通知。
- **FR-113**: 通知 outbox 写入和业务状态变更 MUST 同事务；外部投递失败 MUST 记录可重试状态，不回滚已提交业务。
- **FR-114**: 来源 provider 不可用时，管理页面 MUST 显示明确不可用状态，不得用空数据冒充真实零数据。
- **FR-115**: 所有写接口 MUST 对字段类型、长度、枚举、稳定 ID、版本和角色进行服务端校验，并返回可操作错误。
- **FR-116**: 超级管理员 MUST 能创建、查看和发布系统公告；发布时 MUST 经 02 按明确目标角色或全体用户群发，不得直接写入第二套通知系统。
- **FR-117**: 系统公告 MUST 使用稳定公告 ID 和幂等事件 ID；重复发布不得产生重复用户可见通知，历史公告保留。

### Cross-Module Reuse

- **01 账户与会话**: 直接复用用户表、登录拦截、角色和会话；11 增加账户管理能力，但不创建第二套认证。
- **02 消息通知**: 直接复用审核结果、密码重置和履约事件投递；11 只写 outbox/事件，不直接创建消息中心。
- **03 农业技能**: 复用 `agri_preset_provider` 的读取形状；11 提供权威农产品、农时和病虫害数据。
- **05 非遗技艺**: 复用积分、有效期、奖品、兑换、履约和视频审核 action；11 提供规则、奖品、预置和审核适配器，不复制领域状态机。
- **06 本地资源**: 复用 `local_resource_case_provider` 和现有成功案例表；11 提供管理写入。
- **07 求职就业**: 消费 09 的岗位与申请契约，并可使用 11 的反馈接收契约；11 不修改岗位或申请状态机。
- **08 教师工作台**: 直接接入 11 的统一审核 provider；11 提供课程审核真实现和统计只读点，不接管课程生产。
- **09 企业工作台**: 直接接入 11 的统一审核 provider；11 提供职位审核真实现和跨模块内容管理。
- **10 政务工作台**: 11 复用政策/新闻只读统计，不接管政府发布；当前 010 不消费 11 统计槽。
- **12 AI 学伴**: 11 定义并实现 `assistant_feature_knowledge_provider`；12 后续只依赖该契约接入功能说明知识库。

### Key Entities

- **管理账户**: 01 用户账户的管理视图，包含稳定用户 ID、用户名、姓名、六类角色、启用状态、创建和更新时间。
- **积分规则**: 平台级规则，包含版本、时长折算比率、离散训练权重、每日上限、有效期模式和来源状态。
- **审核记录**: 三类内容的统一审核投影，包含内容类型、稳定内容 ID、提交者、审核状态、版本、驳回意见、发布时间和时间字段。
- **审核队列项**: 审核记录与内容标题、归属、提交时间的展示组合；不拥有第二份业务内容。
- **举报记录**: 评论举报的待处理/确认/驳回状态、理由、处理人、处理时间和结果。
- **意见反馈**: 学员提交内容、状态、处理人、处理结果和时间。
- **预置内容目录项**: 六类内容共有的分类、稳定 ID、启停状态、排序和版本，以及各自领域字段。
- **奖品**: 稳定奖品 ID、名称、积分成本、库存、上下架状态和来源状态。
- **兑换记录**: 用户、奖品快照、积分成本、兑换状态、库存预留、履约和时间信息。
- **履约单**: 与兑换一对一关联，包含待发放、已发放、已核销或已取消状态及动作时间。
- **管理审计记录**: 管理动作、操作者、目标、前后状态、结果和时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 双角色权限矩阵中的每一行均有至少一个正向或拒绝测试；普管越权请求拒绝率为 100%。
- **SC-002**: 普管看板响应递归键扫描中用户类和培训类禁止键出现次数为 0。
- **SC-003**: 超管创建四类管理/业务账户后，新账户在 1 次登录尝试内可用；禁用账户在下一次受保护请求内被拒绝。
- **SC-004**: 密码重置后旧密码失效、新初始密码可用，并且 02 通知或线下交付状态可追踪。
- **SC-005**: 积分规则四个字段的变更测试均在下一次积分计算生效；已发积分到期时间变化数量为 0。
- **SC-006**: 三类审核的通过、驳回、重提、版本冲突和通知测试覆盖率 100%，重复通知数量为 0。
- **SC-007**: 05 适配器测试中，已支持动作映射正确率 100%；首次提交和 `rejected -> pending` 均返回明确冲突，伪造状态数量为 0。
- **SC-008**: 奖品上下架后学员端下一次读取在 1 秒内反映状态；库存预留不会超过配置库存。
- **SC-009**: 取消待发放履约时，积分回退、库存回滚、状态更新和通知 outbox 的成功组合率为 100%，部分提交数量为 0。
- **SC-010**: 评论删除后学员端下一次读取不再返回；被删者收到通知数量为 0。
- **SC-011**: 举报确认和驳回各留下唯一处理结果，重复提交不增加处理量。
- **SC-012**: 六类预置内容的创建、编辑、删除和消费方即时读取测试全部通过。
- **SC-013**: 政策/新闻纠错不改变发布状态，重复订阅推送数量为 0。
- **SC-014**: 全平台数据管理的每类下架/删除动作均通过可见性、历史保留和版本冲突断言。
- **SC-015**: 超管和普管的兑换详情字段一致率 100%，普管从履约上下文读取积分流水与用户账本一致。
- **SC-016**: 所有新增 provider 的注册槽唯一，消费方按具体实现类型分叉数量为 0。
- **SC-017**: 所有新增 provider 的失败路径使用目标错误形状，未捕获数据库错误的用户可见泄露数量为 0。
- **SC-018**: 后台主要页面在桌面和移动宽度无横向溢出，表格、矩阵和长文本不遮挡或截断关键操作。

## Assumptions

- 首个超级管理员在数据库初始化时仅当系统不存在任何 `super_admin` 时创建；用户名固定为 `superadmin`，初始密码来自部署环境变量，不写入仓库。初始凭证通过受控线下渠道交付，首次登录后由用户自行修改。
- 密码重置沿用 01 的“管理员重置初始密码”模式，不提供自助找回；若 02 暂无专用密码重置事件，11 新增事件时必须先保持 02 单一消息中心边界。
- 统一审核队列是一个管理视图，不新增第二份审核状态表；课程和职位的权威状态由 11 通用审核真实现维护，非遗视频权威状态仍在 05。
- 政策下架为状态保留，删除为硬删除并移除浏览量；新闻按 010 当前规则只有发布和硬删除。课程删除、职位删除、视频删除采用逻辑隐藏或 tombstone，以保留学习和业务历史；评论删除为静默隐藏并保留审计。
- 课程、职位和视频的常规生产仍由 08、09 和既有教师/企业流程负责；11 只做审核、纠错和管理动作。
- 意见反馈提交入口不在 11 后台；11 提供接收契约和管理列表，07 学员门户或 12 AI 学伴可在各自 feature 中接入入口。验收期间可通过反馈接收 provider 注入反馈记录验证管理链路。
- 预置内容由 11 权威维护；03、05、06 的现有占位或数据库 provider 不保留第二套正式管理入口。
- 管理员不承担业务内容常规生产，不提供论坛、账户物理删除、政府政策/新闻常规编辑、自助密码找回或第二套消息中心。
- 全平台统计先服务 11 内部看板；010 当前没有消费 11 统计 provider 的槽，若未来需要跨模块读取，应先更新 010 spec。
